# ODIN1 接入

[English](04_odin1_integration.md) | 简体中文

## 已核对的上游情况

[厂商产品页面](https://www.manifoldtech.cn/products/odin1/)描述了 RGB、IMU、点云和位姿输出，列出的 SLAM 精度约为 ±5 cm + 1%。这不保证在本赛道上实现厘米级循线精度，需要验证局部观测和独立测量误差。

[厂商驱动 README](https://github.com/manifoldsdk/odin_ros_driver)推荐 Ubuntu 22.04 上的 Humble，并列明了各版本对应的固件要求。2026-09-10 访问的实时 README 列出驱动 v0.14.4 和固件 v0.14.0，而搜索索引仍显示旧版本。查阅时该 README 尚未正式支持 Ubuntu 24.04。

2026-09-11 已导入驱动 v0.14.4，并记录精确提交；开发笔记本已构建，用户已确认 RViz 点云显示。
详见[厂商接入记录](../vendor_ws/README_cn.md)。该记录明确了本地源码版本，但实物固件及
Jetson 平台组合尚未验收锁定；`racer_odin` 适配层、图像/IMU 质量和整车集成仍待完成。

## 接入顺序

1. 记录传感器型号、设备固件、Jetson 操作系统和架构。
2. 执行前审阅准确的厂商提交及其 ROS 2 构建脚本。
3. 使用 `vendor_ws/src/odin_ros_driver`，保证源码直接位于 ROS 工作空间的 `src/` 下。该底层工作空间与自研包隔离。
4. 匹配固件要求，构建厂商包，把提交 SHA 和构建依据记入 `vendor_ws/README.md` 与平台版本模板。
5. 检查真实话题、消息类型、坐标系、时间戳和 QoS。本文档中的接口名称是适配层约定，不是对厂商话题的假定。
6. 记录静止、缓慢平移、缓慢旋转和地面视野样本。
7. 在 `racer_odin` 中添加明确的重映射和变换，并进行验证。

不要把 ROS 1 启动文件直接复制进本叠加工作空间，也不要无记录地修改上游代码。厂商的 Odin-Nav-Stack 示例基于 ROS 1 Noetic / 宇树 Go2，可参考其集成问题，但不能作为直接可用的 ROS 2 依赖。

## 应记录的观测

| 检查项 | 依据 |
| --- | --- |
| RGB 获取 | 编码、分辨率、曝光和实测帧率 |
| 相机模型 | 设备专属标定与投影模型 |
| 地面可见性 | 最近/最远可用地面距离和黑线像素宽度 |
| 时间 | 采集时钟、主机时钟偏移、传输与处理延迟 |
| 位姿 | 父/子坐标系、复位行为、协方差、静止抖动 |
| TF | 发布者清单和变换方向 |
| 恢复 | USB 插拔、驱动重启和无效数据标记 |
| 计算资源 | CPU/GPU/RAM、USB 带宽和热表现 |

正确使用设备提供的相机模型。未验证校正效果前，不能把广角图像当成理想针孔图像。平面单应性适用于经过标定的地面几何，不能修复任意镜头畸变。保留采集时间戳，不能给旧观测重新打上当前时间来伪装新数据。

## 首个可行性决策

在预期光照下采集包含直线、交叉点和紧弯的短序列。确认可见黑线能投影到稳定地面参考系，且误差满足拟定预算。如果失败，先解决安装/标定问题，或选择符合规则的替代感知方式，再投入高速控制器调参。
